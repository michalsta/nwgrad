# Windows (MinGW-w64)

Windows is built with **MinGW-w64 gcc from MSYS2's UCRT64 environment**, against the official MSVC-built CPython — never MSVC, whose STL has no `<experimental/simd>` (CMakeLists stops an MSVC / clang-cl configure with that message). UCRT64 specifically: CPython links the UCRT, while the runner's preinstalled `C:\mingw64` and Strawberry Perl's gcc link MSVCRT. What the port needed, all in CMakeLists' MinGW blocks unless noted:

- **UCRT required.** An MSVCRT MinGW is not only a second C runtime in the process: its `libmsvcrt.a` links mingw-w64's own x87 `exp` / `log` / `log1p`, whose last bit follows the calling thread's x87 precision-control word — 53-bit on python.exe's main thread, 64-bit on a thread the batch engine starts. Seen in a cross build under wine: batch scores 1 ULP apart between thread counts, logistic probabilities off scipy's `expit`; confirmed with a standalone program (same inputs, `fldcw` 0x27f vs 0x37f, different hashes). UCRT builds import the SSE2 versions from ucrtbase. CMake checks `_UCRT` and stops otherwise; `-DNWGRAD_ALLOW_MSVCRT=ON` overrides, for experiments only.
- **`-static`** on the extension (and every test / benchmark executable): libstdc++, libgcc and winpthread linked in, so the `.pyd` imports only system DLLs, `api-ms-win-crt-*` and `python3XY.dll`. `tools/check_windows_wheel.py` fails the build if it imports a `lib*.dll` or `msvcrt.dll` (the wheel workflow's Windows repair step; `--pyd` mode in `ci.yml`).
- **`MS_WIN64=`** (empty, directory-wide so nanobind's static lib gets it): CPython 3.10/3.11's `pyconfig.h` sets it only under `_MSC_VER`, and without it `Py_ssize_t` is 32-bit. 3.12+ define it for `__MINGW32__` themselves.
- **`-Wa,-mbig-obj`**: COFF's 32767-section cap.
- **`-Wa,-muse-unaligned-vector-move`** on the avx2/avx512 TUs: insurance against GCC PR 54412 (aligned 32/64-byte spills onto Win64's 16-byte-aligned stack). gcc 13 and 16 already emit no aligned vector move with a memory operand in either level object (checked with objdump, 2026-11-01); older gcc did.
- **LLP64:** `long` is 32-bit on Windows. The grid's cell count in `aligner.hpp` (`static_cast<long>(h) * w`), the binding index lambdas in `py_exports.cpp` and the profile counters in `batch_engine.hpp` were `long`; now `long long` / `int64_t`. Keep `long` out of anything that counts cells or indexes.
- **Threads:** `physical_cores()` / `allowed_cpus()` have a Windows branch (`GetLogicalProcessorInformationEx` + `GetProcessAffinityMask`, the latter only on single-processor-group machines); before it the default thread count fell back to logical CPUs, which `parallel.hpp`'s table puts at up to 1.44x slower on SMT hosts.
- **Tests:** the RSS leak test reads the peak working set through `conftest.peak_rss_bytes()` (no `resource` module on Windows); the header-compile test in `test_cli.py` skips a gcc older than 11 (Strawberry Perl's can come first on a runner's PATH).

Not built: win32, win_arm64, and free-threaded `cp3XXt-win*` (pyproject `skip`; the MinGW link against `python3XXt.lib` is untried).

CI: `ci.yml`'s `windows` job (C++ suite with every ISA forced, Python suite on Python 3.11 — the version that exercises `MS_WIN64` — plus the forced-simd pass) and the wheel workflow's `windows-x86_64 (mingw-gcc)` arm, which also runs on PRs touching packaging files.

Verified locally before the first CI run (2026-11-01; Ubuntu's MinGW gcc 16.2 cross-compiler with an MSVCRT runtime, wine 9, an AVX-512 Xeon): the whole C++ suite at the default level (avx512) and `[simd]` forced to avx512 / avx2 / sse4 / sse2 pass; the extension cross-built against CPython 3.11 imports and passes the Python suite but for the four x87 failures above. Not yet measured: speed against the Linux build on the same box (solace, native Windows vs WSL, is the obvious A/B).
